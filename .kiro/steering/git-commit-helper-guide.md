# Git 提交助手使用指南

自动分析代码变更，生成符合 Conventional Commits 规范的提交信息。

## 功能特性

- 🔍 **智能分析**: 自动识别代码变更类型
- 📝 **规范生成**: 生成符合标准的提交信息
- 🎯 **范围识别**: 自动判断影响的模块范围
- ✅ **格式检查**: 确保提交信息格式正确
- 💡 **建议优化**: 提供提交信息改进建议

## 使用方式

### 方式一：自动触发（推荐）

当你说"提交代码"、"commit"、"git commit"等关键词时，助手会自动：

1. 检查当前 git 状态
2. 分析暂存的文件变更
3. 生成规范的提交信息
4. 询问是否执行提交

### 方式二：手动请求

在聊天中直接说：
```
请帮我生成提交信息
请分析变更并提交代码
检查 git 状态并生成 commit message
```

### 方式三：提供上下文

如果你已经知道做了什么，可以提供信息：
```
我添加了 UART 驱动，请生成提交信息
我修复了定时器的 bug，帮我提交
```

## 工作流程

```
1. 检查 git status
   ↓
2. 分析变更文件
   ↓
3. 识别变更类型（feat/fix/docs等）
   ↓
4. 确定影响范围（scope）
   ↓
5. 生成提交信息
   ↓
6. 显示预览并询问确认
   ↓
7. 执行 git commit
```

## 提交信息生成规则

### 自动识别类型

| 变更特征 | 识别为 |
|---------|--------|
| 新增文件/功能 | `feat` |
| 修复 bug、错误处理 | `fix` |
| 修改文档、注释 | `docs` |
| 代码格式化、重命名 | `style` |
| 重构代码结构 | `refactor` |
| 性能优化 | `perf` |
| 添加/修改测试 | `test` |
| 依赖、配置变更 | `build/chore` |

### 自动识别范围

根据文件路径识别：
- `src/uart.rs` → `uart`
- `src/gpio/` → `gpio`
- `docs/` → 省略 scope
- `tests/` → `test`
- `Cargo.toml` → `deps` 或 `build`

### 生成主题描述

- 总结主要变更内容
- 使用动词开头（添加、修复、更新、重构等）
- 保持简洁（不超过 50 字符）
- 使用中文或英文（根据项目习惯）

## 示例场景

### 场景 1: 添加新功能

**变更**: 创建 `src/sensor/dht22.rs`

**生成的提交信息**:
```
feat(sensor): 添加 DHT22 温湿度传感器驱动
```

### 场景 2: 修复 Bug

**变更**: 修改 `src/timer.rs` 中的溢出处理

**生成的提交信息**:
```
fix(timer): 修复定时器溢出导致的系统重启问题
```

### 场景 3: 更新文档

**变更**: 修改 `README.md` 和 `docs/api.md`

**生成的提交信息**:
```
docs: 更新 API 文档和使用说明
```

### 场景 4: 重构代码

**变更**: 重构 `src/interrupt.rs` 的中断处理逻辑

**生成的提交信息**:
```
refactor(interrupt): 简化中断处理流程并提高可读性
```

### 场景 5: 多类型变更

**变更**: 
- 添加新功能 `src/spi.rs`
- 修复 bug `src/i2c.rs`
- 更新文档 `docs/peripherals.md`

**助手建议**: 分成 3 个独立提交
```
feat(spi): 添加 SPI 通信驱动
fix(i2c): 修复 I2C 地址扫描错误
docs: 更新外设使用文档
```

## 交互示例

### 示例 1: 基本流程

**你**: 请提交代码

**助手**: 
```
检查到以下变更：
- 新增: src/uart.rs
- 修改: src/main.rs

建议的提交信息：
feat(uart): 添加 UART 串口通信模块

是否执行提交？(yes/no)
```

**你**: yes

**助手**: 
```
✓ 已提交: feat(uart): 添加 UART 串口通信模块
```

### 示例 2: 需要拆分

**你**: 提交代码

**助手**:
```
检查到多种类型的变更：
1. 新功能: src/sensor.rs
2. Bug 修复: src/gpio.rs
3. 文档更新: README.md

建议拆分为 3 个提交：
1. feat(sensor): 添加传感器驱动
2. fix(gpio): 修复引脚配置错误
3. docs: 更新项目说明文档

是否按此方案提交？(yes/no/custom)
```

### 示例 3: 自定义信息

**你**: 我修复了一个严重的内存泄漏问题，请提交

**助手**:
```
建议的提交信息：
fix: 修复内存泄漏导致的系统崩溃问题

详细描述：
- 修复了 DMA 传输后未释放缓冲区的问题
- 添加了内存使用监控
- 增加了单元测试验证修复

是否使用此提交信息？(yes/edit)
```

## 配置选项

### 自定义提交类型

编辑 `.kiro/steering/git-commit-standards.md` 添加项目特定的类型。

### 自定义范围映射

在提交助手中可以配置文件路径到 scope 的映射规则。

### 语言偏好

- 默认使用中文描述
- 可以要求使用英文：`请用英文生成提交信息`

## 最佳实践

1. **及时提交**: 完成一个逻辑单元就提交
2. **原子提交**: 每个提交只做一件事
3. **清晰描述**: 让别人（和未来的自己）能理解变更
4. **遵循规范**: 保持提交历史整洁
5. **善用助手**: 让 AI 帮你生成规范的提交信息

## 高级功能

### 批量提交

```
请分析所有变更，生成多个提交并依次执行
```

### 修改上次提交

```
请修改上次提交的信息，改为更准确的描述
```

### 查看提交历史

```
显示最近 5 次提交，检查是否符合规范
```

### 生成 Changelog

```
根据最近的提交生成 CHANGELOG.md
```

## 故障排除

**问题**: 生成的提交信息不准确

**解决**: 提供更多上下文信息，或手动指定类型和范围

**问题**: 无法识别变更类型

**解决**: 明确告诉助手你做了什么改动

**问题**: 需要更详细的提交信息

**解决**: 要求添加 body 部分，说明变更原因和影响
